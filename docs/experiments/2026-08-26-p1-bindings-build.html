P1 bindings 產生路徑與建置驗證

日期: 2026-08-26 | 對應階段: 計劃書第 10 章 P1 (Go 介面與橋接層) | 專案位址: github.com/nexgus/fsbrowser

1. 目的

驗證計劃書第 4.4 節所述行為: 外部套件 (本模組 service) 的 Wails v3 service 於宿主 app 執行 wails3 generate bindings 後, bindings 確實產生於 frontend/bindings/github.com/nexgus/fsbrowser/service/ 之下; 並驗證第 10 章 P1 要求的兩個平台建置產物 (Windows amd64, macOS 本機 arch) 皆可成功建置, 且 macOS 產物 可實際啟動並完成一次完整的前端 -> bindings -> Go service 呼叫往返 (含結構化錯誤路徑).

3. 方法

3.1 bindings 產生

於 test/ (最小 Wails v3 app, 以 fsb/memfs 為檔案操作介面實作, 註冊 service.New(...)) 內執行:

cd test
wails3 generate bindings -b ./...

-b 使產生的 bindings 匯入 Wails 內建的 bundled runtime (/wails/runtime.js, 由 Wails 的 asset server 於執行期提供), 前端頁面因此不需安裝 @wailsio/runtime npm 套件或任何建置工具即可 直接以 <script type="module"> 引入 bindings. 未加 -ts 時預設產生一般 JS (含 JSDoc 型別註解), 恰好符合本階段 "前端只需極簡 HTML+JS" 的要求.

3.2 建置

執行 test/build.sh: 腳本先重新產生 bindings (確保與目前 Go 端介面一致), 再分別建置 Windows amd64 (CGO_ENABLED=0 靜態連結交叉編譯, 附 -ldflags "-H windowsgui") 與 macOS 本機 arch (arm64, 正常 cgo 建置) 兩個單一執行檔至 test/bin/.

3.3 macOS 產物啟動驗證

以背景方式啟動 test/bin/fsbrowser-test-macos-arm64, 等待 3 秒後檢查程序是否仍存活, 再手動 結束程序; 同時擷取其標準輸出/錯誤輸出, 確認前端頁面 (test/frontend/index.html) 載入後對 Home / Roots / PathStyle / List / Stat / MakeDir / Rename / Delete 的呼叫鏈實際發生, 並刻意呼叫一次 Delete 於非空目錄, 驗證結構化錯誤 (not_empty) 確實以 err.cause 形式 送達前端.

確認: 外部模組 (github.com/nexgus/fsbrowser/service, github.com/nexgus/fsbrowser/fsb) 的型別與方法確實依 Go import path 產生於 bindings/github.com/... 之下, 與計劃書第 4.4 節的敘述 一致.

過程中的一個發現: 產生過程對 Service.SetFileSystem(fs fsb.FileSystem) 發出警告 parameter fs has non-empty interface type ... passing values other than `null` is not supported by encoding/json. 這是預期行為: SetFileSystem 是供宿主 Go 端於執行期抽換實作用的方法 (計劃書 第 4.4 節), 本非設計給前端呼叫, 介面型別參數無法跨 JSON 邊界傳遞屬正常現象, 不影響其餘八個方法的綁定; 予以保留 不特別處理.

4.3 macOS 產物啟動驗證

啟動後 3 秒程序仍存活 (未崩潰), 手動結束. 標準輸出擷取到以下關鍵行, 顯示視窗成功 建立, 前端頁面成功載入 bindings, 且完整呼叫鏈 (含刻意觸發的錯誤情境) 皆如預期運作:

INF Build Info: Wails=v3.0.0-beta.8 Compiler=go1.26.4 ... GOOS=darwin GOARCH=arm64
INF Platform Info: ID=25F84 Name=MacOS Version=26.5.2
INF AssetServer Info: middleware=true handler=true

INF [AssetFileServerFS] Handling request url=/bindings/.../fsb/models.js
ERR Binding call failed: Bound method returned an error: not_empty: 目錄非空: /home/user/docs

最後一行為刻意觸發的驗證項目 (對非空目錄 /home/user/docs 呼叫 Delete): Go 端 memfs.Delete 正確回傳 fsb.ErrNotEmpty, 橋接層 service.Delete 原樣 回傳該結構化錯誤, Wails 以預設 marshaler 序列化 *fsb.Error (帶 json:"code" / json:"message" tag) 並掛在 CallError.Cause, 前端 @wailsio/runtime 將其還原為 err.cause = {code: "not_empty", message: "..."} 交回呼叫端 -- 此為 service/service.go 註解中所述機制的實機驗證, 非僅程式碼推論. 此行以 ERR 等級記錄 屬 Wails 對 "service 方法回傳非 nil error" 的既有記錄行為, 非本 app 的例外或崩潰.

Windows binary 無法在本開發機 (macOS) 上執行, 依計劃書第 11 章列為殘餘風險, 僅完成建置成功與 file 類型判定兩項, 實際啟動與操作驗證留待可取得的 Windows 環境進行.

5. 結論

  • bindings 產生路徑符合計劃書第 4.4 節所述, 外部模組型別與方法確實產生於 frontend/bindings/github.com/nexgus/fsbrowser/service/ 之下, 附帶其相依的 fsb 套件型別於同層 fsb/ 目錄.
  • Wails v3.0.0-beta.8 對 service 方法 error 的預設處理機制 (json.Marshal 直接序列化 error 值, 包入 CallError.Cause, 前端還原為 err.cause) 已足以承載計劃書第 4.3 節的結構化 錯誤 (代碼 + 訊息), 不需自訂 ServiceOptions.MarshalError; 唯一需要的配合是讓 *fsb.Error 的欄位帶上 json:"code" / json:"message" tag.
  • Windows amd64 與 macOS arm64 兩個單一執行檔皆建置成功; macOS 產物實際啟動並完成一次完整的呼叫鏈驗證 (含正常路徑與結構化錯誤路徑), 未觀察到崩潰.
  • go vet ./..., go test ./... (含 -race) 全數通過.

6. 附註

  • 本次驗證未安裝 WebView2 runtime 於任何 Windows 機器上實測 Windows binary 的啟動與操作, 此為已知殘餘風險 (計劃書第 11 章), 待可取得的 Windows 環境時補齊.
  • test/frontend/bindings/ 為產生物, 未納入版本控制 (視同 node_modules 一類的衍生 檔案); test/build.sh 於建置前會重新執行 wails3 generate bindings, 確保與當時的 Go 端介面同步, 不依賴曾經產生過的舊檔.
  • service/service.go 額外綁定了 SetFileSystem (供 Go 端執行期抽換實作用), 產生 bindings 時對其參數型別 (fsb.FileSystem 介面) 發出警告 (見 4.1 節附註); 該方法本非設計給 前端呼叫, 維持現狀即可.
